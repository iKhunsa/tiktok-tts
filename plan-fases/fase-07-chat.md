# Fase 7 — /chat

## Objetivo
Primer punto de integración multi-dominio real del rebuild. Orquesta el flujo completo de un mensaje: llega crudo de `/canales`, pasa por el veredicto de `/moderacion`, se decide si dispara TTS, se publica ya enriquecido para que `/overlay`, `/sonido`, `/movil` lo consuman.

## Referencia obligatoria
- `arquitectura-propuesta.md`, sección `/chat` — el contrato completo: *"Chat requiere veredicto de moderación ANTES de decidir TTS/overlay"* (contrato síncrono inyectado `moderacionPolicy.evaluate(msg)`, fail-open documentado) y *"Chat nunca llama a Overlay/Sonido directo. Publica chat:mensaje-permitido... Overlay, Sonido, Movil se suscriben."*
- `logging-errores-propuesta.md`, sección `/chat` — eventos `chat.mensaje.emitido` (debug, nunca el texto), `chat.mensaje.bloqueado` (info, con motivo), `chat.policy_fallo_evaluacion` (error).
- `mapa-funciones-actual.md`, sección Chat — funciones a migrar: `resolveDisplayName`/`cleanName`/`isAutoGenerated`/`isUnreadable` (server.js:1179/1097/1106/1110), `sanitizeForTTS` (server.js:1087), `normalizeForModeration` (server.js:1244), `emitChatMessage` (server.js:1489, el orquestador central actual), `isAdminIdentity` (server.js:1475), `POST /api/test/chat` (server.js:2436).

## Detalle por archivo

### clean-name.js / is-auto-generated.js / is-unreadable.js / resolve-display-name.js
Migración directa de server.js:1097/1106/1110/1179. `resolveDisplayName` depende de las otras tres, igual que hoy.

### sanitize-for-tts.js
Migración de server.js:1087 — limpia texto de links/menciones antes de mandarlo a `/sonido`.

### normalize-for-moderation.js
Migración de server.js:1244 — normaliza (minúsculas + espacios) antes de que `/moderacion` evalúe el mensaje. Este archivo es el que arma el `msg` que se le pasa a `moderacionPolicy.evaluate()`.

### is-admin-identity.js
Migración de server.js:1475 — determina si un usuario es admin configurado (consume el snapshot de `/configuracion` vía el contrato de la Fase 2, para leer `adminIdentities` sin importar el store directo).

### emit-chat-message.js — el orquestador
Reemplaza `emitChatMessage` (server.js:1489), hoy el único punto de salida de mensajes de las 3 plataformas. Flujo nuevo:
1. Escucha `bus.on('canal:mensaje-crudo', (raw) => {...})`.
2. Arma el mensaje enriquecido: `resolveDisplayName`, `cleanName`, badge de plataforma, `isAdminIdentity`.
3. Llama **síncronamente** `moderacionPolicy.evaluate(msg)` (contrato inyectado por el core, implementado en `/moderacion` Fase 5). Si esto lanza (no debería, porque `policy.evaluate` ya tiene su propio try/catch interno con fail-open — pero se envuelve igual acá por defensa en profundidad), emite `chat.policy_fallo_evaluacion` (error) y trata el mensaje como permitido.
4. Si `isBanned`/`isMuted`/spam → emite `chat:mensaje-bloqueado` con `{platform, userId, nick, motivo}`, log `chat.mensaje.bloqueado`.
5. Si permitido → `sanitizeForTTS`, arma el payload final, emite `chat:mensaje-permitido`, log `chat.mensaje.emitido` (debug, `{platform, userId, nick, msgId}`, **nunca el texto**).

Este archivo es el corazón de la fase — es el único lugar donde se toca tanto el contrato de `/moderacion` como el bus de salida hacia `/overlay`/`/sonido`/`/movil`.

### routes/test-chat.js
Migración de `POST /api/test/chat` (server.js:2436) — inyecta un mensaje sintético por el mismo camino (`bus.emit('canal:mensaje-crudo', ...)`) que el chat real, para poder probar el flujo completo sin necesitar una conexión real a TikTok/Twitch/YouTube. Log: `chat.test.inyectado` (info) `{platform, user}`.

### index.js
`register({app, bus})`: `bus.on('canal:mensaje-crudo', emitChatMessage)`, monta la ruta de test.

## Criterios de aceptación
1. Inyectar mensajes de prueba (vía `routes/test-chat.js`) para las 3 plataformas, con usuarios normales, admins, muteados y baneados — confirmar que `chat:mensaje-permitido`/`chat:mensaje-bloqueado` salen con el mismo enriquecimiento (badge, nombre resuelto, motivo de bloqueo) que el `emitChatMessage` actual produce para los mismos inputs.
2. Confirmar que un mensaje de un usuario baneado NUNCA llega a `chat:mensaje-permitido` (verificable con un listener de debug temporal suscrito a ambos eventos).
3. Forzar (mock temporal) que `moderacionPolicy.evaluate()` lance una excepción — confirmar que `chat.policy_fallo_evaluacion` se loguea Y que el mensaje de prueba sigue llegando a `chat:mensaje-permitido` (fail-open real, no solo documentado).
4. Ningún log de este dominio (`chat.mensaje.emitido`/`bloqueado`) contiene el texto del mensaje, solo identificadores.
5. Con `/moderacion` (Fase 5) y `/canales` (Fase 6) ya montados junto con este dominio, un mensaje real de un canal de prueba conectado debe recorrer el flujo completo end-to-end: canal → chat → (moderación) → chat:mensaje-permitido, visible en los logs de las 3 fases encadenadas.

## Riesgos
- Este es el primer punto donde una fase depende de que DOS fases anteriores (`/moderacion` y `/canales`) estén completas y correctamente inyectadas por `/core` — si alguna quedó con un contrato mal definido, el fallo aparece recién acá. Antes de empezar esta fase, confirmar explícitamente que `core.provideContract('moderacionPolicy', ...)` (Fase 5) y los eventos `canal:*` (Fase 6) ya están verificados de forma aislada.
